# 요청·응답 로그

개선된 소스를 실행하거나 이 변경이 포함된 새 앱으로 업데이트하면 적용됩니다. 이미 실행 중인 프로세스에는 소스 변경만으로 적용되지 않습니다. 이전에 공증한 앱 ZIP을 수정하거나 기존 서명을 재사용하지 않습니다.

## 터미널에서 보는 내용

요청이 들어오면 `REQ`, 끝나면 `RES OK` 또는 `RES ERROR`가 나옵니다. 두 줄의 대괄호 ID가 같으면 같은 요청입니다. 다음은 형식을 설명하는 예시입니다.

```text
16:46:51.341 [aac8a718-3] REQ read_file {"arguments":{"path":"sample.txt"}}
16:46:51.360 [aac8a718-3] RES OK read_file {"duration_ms":19.0,"text_chars":97,"images":0}
16:46:51.407 [aac8a718-7] REQ read_file {"arguments":{"path":"[outside workspace]/outside.txt"}}
16:46:51.407 [aac8a718-7] RES ERROR read_file {"duration_ms":0.3,"error_code":"outside_workspace"}
```

| 표시 | 의미 |
| --- | --- |
| `REQ` | 어떤 MCP 도구가 어떤 대상/옵션으로 요청됐는지 요약합니다. |
| `PHASE` | 로컬 승인 대기(`approval_wait`), 소유자가 선택한 자동 승인(`auto_approved`) 등을 표시합니다. |
| `WAIT` | 5초 이상 진행 중이면 한 번, 이후 15초 간격으로 경과 시간을 알립니다. 진행 중이라는 뜻이며 실패로 단정하지 않습니다. |
| `RES OK` | 도구 호출이 정상 응답했습니다. 시간(ms), 응답 글자 수, 이미지 수와 안전한 상태/개수 정보를 표시합니다. |
| `RES ERROR` | 정책 거부·입력 검증 오류·없는 파일·연결 오류 등을 정해진 오류 코드로 표시합니다. |
| `RES CANCELLED` | 요청이 취소됐습니다. 이미 일어난 외부 작업을 취소/복구했다는 뜻은 아닙니다. |

`duration_ms`는 서버가 해당 도구 호출을 처리한 시간입니다. 모델의 생각 시간, ChatGPT와 터널의 왕복 시간까지 포함한 전체 작업 시간이 아닙니다.

`start_process`는 기본 `wait=complete`에서 프로세스 종료까지 기다리므로 정상 종료를 관측하면 같은 `RES`에 `process_state=completed`와 `reported_exit_code`를 기록합니다. `wait=start`를 썼거나 안전 대기 한도에 도달해 아직 실행 중이면 `process_state=started`로 남고, 이후 `process_output`에서 종료 코드를 확인할 수 있습니다. `RES OK`는 MCP 도구 호출 자체의 정상 응답을 뜻하며 셸 종료 코드 0을 대신하지 않습니다. 종료 코드는 엔진 응답에서 읽은 값이며 독립적인 OS 검증은 아닙니다.

영상 확인은 일반 프로세스로 기록됩니다. 기본 대기에서는 `start_process` 응답에 `started/progress/complete/error/cancelled` 진행 이벤트와 종료 코드가 포함되며, 분리 실행한 경우에는 `process_output`으로 이어서 확인합니다. 이미지 데이터 자체는 기록하지 않습니다. 이 로그는 MCP 도구 실행 기록이며, ChatGPT 대화 원문·모델 추론 과정·모든 HTTP 패킷을 기록하는 기능이 아닙니다. 터널 내부의 command/workflow ID가 MCP 요청에 전달되지 않으면 임의로 연결했다고 표시하지 않습니다.

## 기록하지 않는 것

메일/블로그 본문, 입력한 텍스트, 파일의 원문/수정 내용, 반환된 파일·페이지·터미널 출력 원문, 이미지 base64, 쿠키, 인증 헤더를 요청 로그에 저장하지 않습니다. 본문은 글자 수만 남깁니다.

셸 명령은 **프로그램·서브커맨드·일반 플래그·작업 폴더 기준 경로 등 실행 흐름을 이해하는 데 필요한 인자**를 표시합니다. 대신 환경변수 값, API 키·토큰·비밀번호·쿠키·Authorization 헤더, HTTP 폼/본문, `echo`/`printf` 내용, 검색 패턴, `python -c`/`node -e`/셸 `-c`와 heredoc 같은 인라인 코드·스크립트는 자동으로 마스킹합니다. 이 표시는 완전한 셸 원문이 아니라 안전한 미리보기입니다. 웹 주소는 사이트의 스킴과 호스트만 남기며 경로·계정정보·쿼리·프래그먼트는 제외합니다. 클릭 대상은 관측된 요소 참조만 표시하고 임의 선택자와 요소 설명은 숨깁니다. 알려지지 않은 필드는 내용 대신 개수만 기록합니다.

SDK가 입력 검증 오류에 잘못된 입력값을 다시 출력하는 경우도 있으므로, MCP SDK의 가변 진단 문자열/예외 스택은 로컬 로그에서 제외합니다. 경고·오류 수준은 유지하며, 실제 도구 응답은 수정하지 않습니다. 자세한 오류는 요청한 대화의 도구 응답으로 확인하세요.

파일 경로·사이트 호스트·실행 시각 자체도 민감한 메타데이터일 수 있습니다. 경로에 대한 일부 키/이메일 패턴 제거는 완전한 개인정보 탐지기가 아닙니다. 로그 전체를 공개 이슈에 붙이지 말고 필요한 줄만 검토해서 공유하세요. Desktop Commander·터널 클라이언트의 별도 기존 로그를 모두 비식별화하는 기능은 아닙니다. 원문 HTTP 로깅 옵션은 켜지 않습니다.

## 저장 위치와 크기

사람이 읽는 로그는 **stderr**로 출력합니다. MCP 프로토콜이 사용하는 **stdout**에는 로그를 쓰지 않습니다. 터미널 실행에서는 해당 터미널, 앱 실행에서는 기존 **MB → 로그 보기**에서 stderr가 수집되는 `app.log`를 확인할 수 있습니다.

별도로 구조화된 JSONL을 저장합니다.

- 소스 실행: `<실행 루트>/.state/request-logs/requests.jsonl`
- 독립 앱: `~/Library/Application Support/Computer Controller/.state/request-logs/requests.jsonl`

현재 파일 약 2 MB와 이전 파일 두 개를 순환 보관합니다. 파일은 소유자 전용 권한(600), 폴더는 700이며 Git에 포함되지 않습니다. 여러 프로세스의 파일 기록/순환은 파일 잠금으로 직렬화합니다. 심볼릭 링크·하드링크 로그 파일은 따라 쓰지 않습니다. 디스크가 가득 차거나 기록에 실패해도 도구를 재실행하거나 성공한 작업을 실패로 바꾸지 않습니다. 기록을 못 했다는 고정 경고만 남깁니다.

JSONL에는 세션 ID, 서버 PID, 요청 상관 ID, 가능한 경우 MCP의 숫자 요청 ID도 포함됩니다. MCP 요청 ID가 반복되어도 내부 요청 ID는 구분되며, 자유 문자열 MCP ID는 원문 대신 해시 요약으로 남깁니다.

## 터널 잡음 줄이기

소스 실행의 기본 터널 로그 수준을 `warn`으로 낮춰 반복되는 dispatcher 전달 메시지를 줄였습니다. 실제 경고와 오류는 남습니다. 연결 자체를 진단해야 할 때만 다음처럼 이전 수준을 복원할 수 있습니다.

```sh
bash Mac-Start.command --tunnel-log-level info
```

독립 앱은 기존처럼 터널 `warn` 수준을 사용합니다. MCP SDK의 `Processing request of type CallToolRequest` 문구는 의미 있는 요청/응답 로그로 대체합니다.

## 검증

```sh
python -m unittest discover -s tests -p 'test_*.py' -v
python tests/smoke_request_logging.py
```

단위 검사는 본문/키 패턴 숨김, 회전·파일 권한, 동시 요청 상관 ID, 예외·취소·승인 단계, 로그 실패 시 결과 보존을 다룹니다. 실제 stdio 검사는 임시 작업 폴더에서 MCP/엔진을 실행해 정상·거부·입력 오류를 호출하고, stdout 프로토콜과 응답이 유지되며 테스트용 비밀 문자열이 로그에 없는지 확인합니다. 현재 실행 중인 사용자의 터널이나 개인 브라우저를 재시작하는 검사가 아닙니다.

현재 프로젝트의 MCP SDK 1.28.0의 최종 요청 처리 함수를 감싸므로 입력/출력 검증 이후의 도구 오류도 기록합니다. SDK 버전 변경 시 이 통합 검사를 다시 실행해야 합니다.
